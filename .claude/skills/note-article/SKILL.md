# note記事作成スキル

このスキルは、このリポジトリのCLAUDE.mdに定義された運用ルールを、抜け漏れなく順番通りに実行するための手順書です。
文体ルールや禁止表現など内容そのものの正は `docs/` 配下のファイルにあります。ここでは重複を避け、「何をどの順番でやるか」だけを扱います。

## トリガー

次のような依頼が来たら、このスキルの手順で最後まで進める。テーマが指定されていなくても、ユーザーに選ばせるために止まらず、自分で妥当なテーマを選んで進めてよい。

- 「記事作成して」「次の記事書いて」「noteの記事お願い」
- 「〇〇についてnote書いて」（〇〇はテーマ指定あり）
- 「就活ニュースの記事書いて」

## 手順

以下を順番に実行する。途中の確認ステップを飛ばして本文から書き始めない。

### 1. 文体ルールを確認する

`docs/style-guide.md` を読む。ペルソナ・読者像・トーン・よく使う言い回し・絶対に使わない表現・分量目安（5,000〜6,000字）を頭に入れる。

### 2. フィードバックを確認する

`docs/feedback-log.md` を読み、直近のフィードバックで今回の記事に未反映のものがないか確認する。あれば先に反映方針を決めてから執筆に入る。

### 3. テーマを決める

- ユーザーがテーマを指定していれば、それを使う。
- 指定がなければ `docs/topic-backlog.md` の「未着手」から、読者（大学3・4年生の就活生）にとって時期的に適切なものを選ぶ。または、就活の最新動向から `docs/topic-backlog.md` にまだないテーマを提案し、表に追記してから使ってもよい。
- どちらの場合も、ユーザーに選択を委ねるために止まる必要はない。自分で決めて進める。

### 4. 執筆する

該当カテゴリの `articles/<category>/` 配下に、英語スラッグのファイル名（例: `fermi-estimation.md`）で `.md` を1本作成する。
`docs/style-guide.md` のトーン・言い回し・禁止表現ルールに沿って書く。分量目安は5,000〜6,000字（本文のみ、見出し込み）。

実体験の語りだけで記事を埋めないこと。`docs/style-guide.md`の「実体験と専門性のバランス」に従い、共感を作る実体験パートと、しっかり調べて書いたように読める専門性パート（フレームワークの定義、構造的な整理・比較など）の両方を組み込む。

技術・コツを説明する箇所は、`docs/style-guide.md`の「指針としてのノウハウの示し方」に従い、「ポイントは◯つあります」のように要点を数で区切り、それぞれ読んだ直後に実行できる具体的な行動まで書く。曖昧な提案（「〜すればいいのでは」）で終わらせない。

タイトルは`docs/style-guide.md`のタイトル方針に従う。タイトルは本文なしでXに単独投稿されて集客に使われるため、実体験の振り返り調（「〜だった」「〜という話」で終わるしみじみ系）だけの弱いタイトルにしないこと。本文が「ポイントは◯つ」構成なら、その数をそのままタイトルに出す数字訴求型を優先する（例：「〜3つのコツ」）。「〜の人へ。」を毎回使うと購読意欲を刺激しにくいという指摘もあるため、直近の記事と同じ型を続けて使わないこと。

検証できない具体的すぎる「事実」（特定のテストの出題形式、統計値など）を本人の実体験として断定しないこと。一般的に成り立つ考え方・練習法として書くか、断定を避けた表現（「〜と言われているらしい」など）にする。これは過去のフィードバックで得た教訓で、`docs/feedback-log.md` に記録済み。

### 5. セルフチェックする

`docs/style-guide.md` のセルフチェックリストで確認する。特に次の点は機械的にも確認する。

- 禁止表現（「本記事では」「結論として」「まとめると」「〜することが重要です」「誰でも」「必ず」「絶対に稼げる」「一瞬で変わる」「今すぐやらないと」「驚くほど」「革命的な」）が入っていないか
- 一文が長くなりすぎていないか
- 実体験ベース・横並め目線のトーンになっているか

文字数は感覚で判断せず、必ず実際にカウントする。

```
python3 -c "print(len(open('<ファイルパス>', encoding='utf-8').read()))"
```

5,000〜6,000字の範囲になっているか確認し、大きく不足している場合は、水増しではなく別の具体例やQ&Aを1つ足して厚みを出す。note投稿時はMarkdown記号が取り除かれてこの数値より少し減る（詳細は`docs/style-guide.md`の「分量の目安」）。

さらに、`docs/style-guide.md`の「ファクトチェックと効果性チェック」を必ず実施する。事実主張の裏取り状況（一般に知られた知識か、断定を避けるべき情報か）と、書いたテクニックが読者にとって実際に役立つ具体的な内容になっているかの両方を確認する。省略しないこと。

問題があれば本文を直してから次に進む。

### 6. バックログを更新する

`docs/topic-backlog.md` の該当行のステータスを `初稿済み` に更新する（実際にnoteへ投稿してから `公開済み` にする運用なので、この時点ではまだ変えない）。新規テーマだった場合は行を追加する。

### 7. フィードバックを記録する

今回のやりとりの中でユーザーから新しい指摘や気づきがあれば、`docs/feedback-log.md` に追記する。特になければこのステップは省略してよい。

### 8. コミットしてpushする

変更したファイル（記事本体、topic-backlog.md、必要ならfeedback-log.md）をgit commitし、現在の作業ブランチにpushする。コミットメッセージは記事の内容が分かるものにする。

### 9. note投稿手順を提示する

このリポジトリからnote.comへ直接投稿することはできない。`CLAUDE.md` の「noteへの実際の投稿手順」に従い、次の2つをユーザーに提示して完了とする。

- 今回作成したファイルのGitHub上のURL。`https://github.com/<owner>/<repo>/blob/<作業ブランチ名>/<ファイルパス>`の形で、途中を省略せず完全な形で提示する。記事はmainブランチには存在しないため、ブランチ名を省略したり「続きはこちらに」のような形で相手に組み立てさせたりすると404になる（実際に起きた事例が`docs/feedback-log.md`にある）
- Chrome版Claude（Claude for Chrome拡張機能）に渡す依頼文テンプレート（CLAUDE.md記載のものをこの記事のテーマに合わせて調整する）

## このスキルの範囲外のこと

- note.comへの実際のログイン・記事入力・公開ボタンを押す操作（Chrome版Claudeで別途行う）
- 見出し画像の実データ作成（画像生成ツールはこの環境にないため、方向性の提案までにとどめる）
