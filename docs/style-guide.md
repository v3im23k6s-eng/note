# 文体ルール（本文を書く前に必ず確認）

このガイドは「フルトレ就活」note記事を書く前に**毎回**確認するルールです。
記事本文を書き始める前に必ずこのファイルと `docs/feedback-log.md` を読み、直近のフィードバックを反映してください。

ここに書かれているペルソナ・読者像・トーン・言い回し・禁止表現・分量の目安は、今後の記事すべてに共通して適用する固定ルールです。
一方で扱うテーマ自体は固定ではなく、就活に関することであれば`docs/topic-backlog.md`にないテーマ・最新ニュース・新しい言葉も積極的に扱っていきます（詳細は `docs/topic-backlog.md` を参照）。

## 発信者のペルソナ

- Xアカウント名: フルトレ就活
- 実績: 日経大手四社から内定（実体験ベースで語れる）
- 専門分野: デザイン思考テスト（受験数が少ないにもかかわらず高得点）
- 支援領域: ES、面接、SPI、自己分析、OB訪問、業界研究など就活全般

## 読者像

- 大学3年生・4年生の就職活動者
- まだ手探りの人も、ある程度進めている人も両方含む

## トーンの基本方針

- **読者の横で一緒に進む感覚**で書く。上から目線で「教える」のではない。ただし、これは高圧的・断定的な物言いを避けるという意味であり、ノウハウ自体を曖昧にぼかすという意味ではない。技術やコツの部分は、下の「指針としてのノウハウの示し方」に沿って、教科書のように明確に示す。
- 「私もそうでした」のように、自分の実体験を根拠にする。
- 断定で押しつけるのではなく、事実ベースで淡々と伝える。
- 一文は短く。長くなったら切る（一文一義を意識する）。

## 実体験と専門性のバランス

記事全体を実体験の語りだけで埋めないこと。実体験だけの記事は、日記のように読めてしまい、300円を払ってでも読みたいと思える「専門性のある情報」としての価値が弱くなる。

1記事の中で、次の2種類のパートを両方意識して組み合わせる。

- **実体験パート**：「私もそうでした」「自分はこうしていました」のような、一人称の語り。読者との距離を縮め、共感を作る役割。
- **専門性パート**：フレームワークの定義や成り立ち、一般的に知られている考え方、構造立てた整理・比較など、しっかり調べて書いたように読める解説。読者が「お金を払って読む価値がある」と感じる情報の厚みを作る役割。

専門性パートを書くときも、`docs/feedback-log.md`に記録した「検証できない具体的すぎる事実を断定しない」ルールは変わらない。特定の企業やテストの詳細のような裏取りできない情報を断定するのではなく、広く知られているフレームワークの説明・一般的な考え方の整理・構造的な比較など、裏取りしなくても成り立つ範囲で専門性を出す。

執筆時のイメージとしては、導入や具体例では実体験の語り口を使い、フレームワークの説明や整理のパートではより解説記事らしい、落ち着いた専門的なトーンに切り替える、というように使い分ける。

## 指針としてのノウハウの示し方

「なんとなく良さそう」で終わる記事ではなく、読んだ直後にそのまま実行できる、教科書のような明確さを持たせること。「こうすればいいのでは」のような曖昧な提案で終わらせず、要点を数で区切って明言する。

- 技術・コツを説明するときは、「ポイントは3つあります。1つ目は〜、2つ目は〜、3つ目は〜です」のように、要点の数を先に宣言してから一つずつ説明する構成を積極的に使う。数はテーマに応じて2〜5個程度で調整してよい。
- 各ポイントは、抽象的な心構え（「意識しましょう」）で終わらせず、読んだ直後に真似できる具体的な行動・言い回し・チェック基準まで書く。たとえば「相手の立場で考える」ではなく、「相手に『それをやると何が変わりますか』と聞き返してみる」のように、実際にやることが分かる粒度まで下ろす。
- 「〜かもしれません」「〜という感じもします」のような二重の曖昧化は、技術・手順を説明する文では避ける。感想や実体験の余韻を伝える文（さいごに、など）では引き続き使ってよい。
- 「〜することが重要です」という言い切りの締め方は禁止表現のままだが、「重要なポイントは3つあります」のように要点を列挙する構成は、この禁止表現とは別物として積極的に使ってよい。前者は具体性のない精神論の締めくくり、後者は具体的な手順を導くための構成、という違いがある。

## よく使う言い回し（積極的に使う）

- 「〜で大丈夫です」
- 「〜でオッケーです」
- 「〜という感じです」

## 絶対に使わない表現

以下は禁止。言い換える。

- 「本記事では」
- 「結論として」
- 「まとめると」
- 「〜することが重要です」
- 「誰でも」
- 「必ず」
- 「絶対に稼げる」
- 「一瞬で変わる」
- 「今すぐやらないと」
- 「驚くほど」
- 「革命的な」

こうした表現は煽りや上から目線に読まれやすいため、事実と実体験ベースの語り口と相性が悪い。書いてしまったら別の言い方に置き換える。

## 分量の目安

- 1記事あたり5,000〜6,000字程度（本文のみ、見出し込み）。下限の5,000字は大きく下回らないように厳守する。上限の6,000字は「深みのあるノウハウを盛り込んだ結果、伸びるのは構わない」という意味で、水増しして6,000字まで埋める必要はない。
- note投稿時はMarkdownの記号（`#`や`*`など）が取り除かれるため、このリポジトリ内のMarkdownファイルの文字数は、noteに実際投稿したときの文字数より少し多く出る。過去の実績では、Markdownファイルで約3,800字だった記事が、note投稿時には約3,700字になった（差はおよそ100〜150字程度）。
- そのため、執筆後は必ず文字数を実際にカウントし、Markdownファイルの時点で5,000〜6,000字の範囲に収まるように調整してから完成とする。目視の感覚だけで「だいたいこれくらいだろう」と判断しないこと。
- カウント方法の例（このリポジトリの環境で実行できる）:
  ```
  python3 -c "print(len(open('<ファイルパス>', encoding='utf-8').read()))"
  ```
- 5,000字に対して大きく不足している場合は、内容を薄めて水増しするのではなく、「指針としてのノウハウの示し方」に沿った具体的な技術・チェックリスト・Q&Aなどを追加して厚みを出す。

## 販売形態とタイトルの付け方

記事は1本あたり300円程度でnote上で販売する。無料で読める記事ではないので、タイトルは「これは読む価値がありそう」「続きにお金を払ってもいい」と思ってもらえるように工夫すること。

**タイトルはX（旧Twitter）に単独で投稿して集客する。** 本文どころか冒頭の一文すら一緒には表示されない前提で考えること。タイトルだけを見た人が、「クリックして中身を見たい」「ノウハウが詰まっていそう」と感じられるかどうかが、記事が読まれるかどうかをほぼ決める。実体験の述懐（「〜だった」「〜という話」で終わる、しみじみとした振り返り調）だけの弱いタイトルにしないこと。

- 読者が抱えていそうな悩み・不安・具体的な状況を想像させる
- 読んだ後に何が得られるかが伝わるようにする（考え方が分かる、迷わなくなる、など）
- 禁止表現・煽り表現は使わない。「驚くほど」「revolutionary」的な誇張ではなく、等身大の実感で価値を伝える
- タイトルだけで内容の核心を全部言い切らない。続きを読みたくなる余地を残す
- 「〜の人へ。」という定型文を毎回使わない。同じ形が続くと購読意欲を刺激しにくい

**本文が「ポイントは◯つあります」の構成になっている記事は、その数をタイトルにそのまま出す。** 「3つのコツ」「4つの手順」のように具体的な数を出すと、ノウハウが詰まっている印象が強まり、クリック率が上がりやすい。ただし、タイトルで出した数と本文の見出し数が一致していることを必ず確認する（一致していないと開いた読者ががっかりする＝効果性チェックの対象）。

タイトルの型は、記事の内容に応じて次から選ぶ。同じ型を連続で使わない。

- 数字訴求型：「〜3つのコツ」「〜4つの手順」「〜3つのチェックポイント」（本文がポイント構成のときに優先）
- 前提を覆す型：「〜だと思っていたら、実は違った」
- 気づき型：「〜なのは、○○のせいだった」
- ビフォーアフター型：「〜が、○○を知ってから変わった」
- 疑問形：「〜って、結局何なのか」

タイトルを決めたら、次の2つを両方確認してから本文に進む。

1. 「このタイトルだけをXで見て、クリックして中身を見たいと思えるか」（実体験の振り返り調で終わっていないか）
2. 「直近数本のタイトルと同じ型になっていないか」

## 目次を必ずつける

タイトルの直後、本文（導入の書き出し）より前に、その記事のH2見出し（`##`）を上から順にすべて箇条書きにした「目次」セクションを置く。形式は次の通り。

```
# タイトル

## 目次

- 見出し1
- 見出し2
- （以下、本文中のH2見出しをすべて上から順に）

導入の書き出し...
```

- 見出しの文言は本文の`##`見出しと完全に一致させる（省略・言い換えをしない）。見出しを追加・変更したら目次も必ず更新する
- リンクや番号は付けず、シンプルな箇条書きにする（note編集画面へ転記したときに崩れにくいため）
- この目次セクション自体は文字数のカウント対象に含めてよい（分量の目安に大きな影響はない）

## ファクトチェックと効果性チェック（執筆後に必ず実施）

執筆後は、禁止表現や文字数のチェックに加えて、次の2種類のチェックを必ず行う。省略しないこと。

**ファクトチェック**：本文中の事実主張を一つずつ洗い出し、次の基準で確認する。

- 一般に広く知られているフレームワーク・制度の説明（社会人基礎力の12要素、MECEの定義など）か → 事実として断定してよい
- 統計値・特定企業の内部事情・特定テストの出題形式など、裏取りできない情報か → 断定を避け、「〜と言われている」のように出典不明であることが伝わる書き方にするか、思い切って削る
- 自分（発信者）の実体験として書いている内容か → 本人が実際に体験した・体験しうる範囲を超えていないか確認する。範囲を超えていたら、一般論として書き直す

**効果性チェック**：書いたテクニック・アドバイスを一つずつ見て、次を自問する。

- 読者が実際のES・面接・自己分析の場面でそのまま使えるか（抽象的な心構えで終わっていないか）
- そのアドバイス通りにやって、本当に読者の役に立つか（もっともらしいだけで効果が薄い一般論になっていないか）
- 他の記事のテクニックと重複するだけで、この記事ならではの情報になっていないか

引っかかった箇所があれば、公開前に必ず修正する。この2つのチェックは今後すべての記事で実施する固定ルール。

## 執筆フロー

1. `docs/style-guide.md`（このファイル）を読む
2. `docs/feedback-log.md` を読み、直近の指摘事項を確認する
3. `docs/topic-backlog.md` からテーマを選ぶ、または新規テーマを追加する
4. 該当カテゴリの `articles/<category>/` 配下に記事を作成する
5. 執筆後、禁止表現・文字数（5,000〜6,000字）に加えて、上記の「ファクトチェックと効果性チェック」を実施する（問題があれば加筆・修正する）
6. フィードバックをもらったら `docs/feedback-log.md` に追記し、次の記事から反映する
