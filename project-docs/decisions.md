# 決定事項ログ

## D1. 実現方式はA案(GitHub Pages静的ページ)を採用

- 決定内容: claude.ai内蔵Artifactとしてではなく、このリポジトリの`docs/`配下に静的HTML/JSを置き、GitHub Pagesで公開する。生成はClaudeとの手動コピペ往復。
- 決定理由: claude.ai内蔵ストレージ機能の不具合(過去の設定リセット・重複生成の疑わしい原因)を回避し、ブラウザ標準のlocalStorageで確実に状態を保持するため。スマホの複数ブラウザ(Safari/Chrome)でも同様に動作することを確認済み。
- 検討した代替案: B案(引き続きclaude.ai内蔵Artifactとして構築、バックアップ機能で保険をかける)。ワンクリック生成を維持できる利点はあるが、根本原因を解消できる保証がないため不採用。
- 決定日: 2026-08-17
- 後から見直す条件: Anthropic側のartifact内蔵ストレージの信頼性が改善された、またはコピペ往復の手間が運用上耐えられないと判明した場合。

## D2. Xへの自動投稿は実装しない

- 決定内容: 生成のみを対象とし、実際の投稿は利用者が手動でコピー&ペーストする。
- 決定理由: 利用者の希望(APIキー管理を避けたい、コピペで十分)。また元ツールもX利用規約上のリスクを理由に自動投稿を意図的に避けていた経緯があり、その方針を踏襲する。
- 検討した代替案: X公式APIによる半自動投稿(生成→確認→ワンタップ投稿)。将来的な拡張候補として残すが、今回は見送り。
- 決定日: 2026-08-17
- 後から見直す条件: 利用者からX公式APIを使った投稿の明示的な依頼があった場合。

## D3. 1回あたりの生成件数を6〜8件に拡大

- 決定内容: 生成件数の選択肢を「2・3件」から「6・7・8件」に変更(既定6件)。
- 決定理由: 利用者が1日1回まとめて作業したいと明言したため。
- 決定日: 2026-08-17
- 後から見直す条件: 生成品質(重複・偏り)がこの件数で悪化すると分かった場合。

## D4. account_profile.pyの内容はペルソナ欄のデフォルト文に翻訳して反映する

- 決定内容: `analysis/account_profile.py`(構造化データ)とは別に、その内容を人間が読める文章に書き直し、`docs/app.js`内の`DEFAULT_PERSONA`として反映する。
- 決定理由: ブラウザは`.py`ファイルを直接読み込めず、ツールの設定欄は自由記述のテキストのため。account_profile.py自体は分析結果の記録として保存する。
- 決定日: 2026-08-17

## D5. ディレクトリ構成の分離(docs / analysis / project-docs)

- 決定内容: `docs/`をGitHub Pages公開専用、`analysis/`を分析成果物専用、`project-docs/`を設計文書専用として分離。
- 決定理由: GitHub PagesのデフォルトソースフォルダがDocsであるため、企画文書用の`docs`という名前と衝突しないようにするため。
- 決定日: 2026-08-17

## D6. 文字数カウントをサロゲートペア対応に変更(元ツールからの改善)

- 決定内容: `str.length`ではなく`Array.from(str).length`で文字数を数える。
- 決定理由: 元ツール(PDF11章)は絵文字等のサロゲートペアを考慮しない簡易カウントだったと明記されていたため、既知の限界として改善した。
- 決定日: 2026-08-17

## D8. 画像対応は「自作テキストカード」+「外部ツール向けプロンプト」の2本立て

- 決定内容: (a)投稿文をcanvasで描画したブランドカラーのカード画像をダウンロードできる機能と、(b)外部の無料AI画像生成ツール(Bing Image Creator/Canva等)に貼り付けるプロンプトを作る機能、の2つを用意した。AI画像生成APIそのものは組み込まない。
- 決定理由: 利用者から「バズっているアカウントは画像(特に文字を大きく見せるテキストカードや、企業ロゴ・ビルの写真風画像)を使っている」というフィードバックがあった。テキストカードはブラウザだけで確実に作れAPI不要。実在の企業ロゴ・建物写真をそのまま使うのは著作権・商標のリスクがあるため、写真風の画像が欲しい場合は「雰囲気を伝えるイラスト」を外部ツールで生成する前提のプロンプトに留めた。
- 検討した代替案: 実在の企業ロゴ・建物写真を自動収集して貼り付ける方式は、権利侵害リスクが高いため不採用。専用の画像生成APIを組み込む方式は、追加のAPIキー・費用が必要になり「APIは扱いたくない」という方針と矛盾するため不採用。
- 決定日: 2026-08-19
- 後から見直す条件: 利用者が画像生成APIの導入コストを許容する場合、または著作権上問題ない画像素材の使い方が別途見つかった場合。

## D9. 300〜400字の「画像化投稿」モードと白地カードデザイン

- 決定内容: 140字に収まらないが厚みのある内容(300〜400字)は、無理にスレッド分割せず「画像化投稿」として①短い導入文(ツイート本文)と②長い本文(画像化)の2つに分けて生成できるようにした。画像カードの背景は白地・文字はダーク基調+要点のみカラー(❌⭕・番号など)に変更(以前はダーク背景だった)。
- 決定理由: 利用者から「バズっている就活アカウントは、文字数が入らない内容を画像内にたくさん書き、ツイート本文はクリックしたくなる短い導入文にしている」というフィードバックがあった。また「文字を書く場合は白地で、視認性を意識してほしい」という明示的な指定があった。
- 検討した代替案: 引き続きスレッド機能(複数投稿への分割)のみで対応する案。読む側の体験(画像1枚の方が完結して見やすい)と、利用者の要望を踏まえてボツにした。
- 決定日: 2026-08-19
- 後から見直す条件: 画像化投稿の使用感が悪い、または白地デザインが読みにくいと利用者が感じた場合。

## D10. 画像化投稿の文字数と比率を利用者指定の数値に変更、コード側で強制割当

- 決定内容: 画像化投稿のfullTextを300〜400字→400〜500字に変更。また1回の生成(8件なら8件)のうち、文字だけの「通常投稿」を2件、残りを「画像化投稿」にする比率を、タイプ・キーワードと同じく`assignFormats()`でコード側が確定させ、指示文に「◯件目: 形式:画像化投稿/通常投稿」と明記するようにした。
- 決定理由: 利用者からの明示的な数値指定。以前の「0〜1件が目安」というAI任せの緩い指示では守られない可能性があったため(タイプ・キーワードの割当を"目安"から"強制"に変えた時と同じ理由)、比率を厳守させるためコード側で確定させる方式にした。
- 決定日: 2026-08-19
- 後から見直す条件: 利用者から比率や文字数の再指定があった場合(`TEXT_ONLY_RATIO`定数と`400〜500字`の記述を変更するだけで対応可能)。

## D11. hookTextの作り方を具体的な型として指示文に明記

- 決定内容: 画像化投稿のツイート部分(hookText)について、「続きは画像で」のような定型句だけに頼らず、①具体的な数字を見せる、②結論を伏せて情報のギャップを作る、③自分の実体験・実績に紐づける、という3つの型を指示文に明記した。誇張・煽りは引き続き禁止。
- 決定理由: 利用者から「画像は良い出来だが、それを読んでもらうにはツイート部分(hookText)の工夫が要る」というフィードバックがあった。画像化投稿は開いて初めて内容が伝わるため、hookTextの質が読了率を左右する。
- 決定日: 2026-08-19

## D7. Xの下書きを開くボタンにWeb Intentを採用

- 決定内容: `https://x.com/intent/tweet?text=...`形式のリンクで、Xの投稿作成画面に本文を差し込んだ状態を開けるボタンを追加。
- 決定理由: 認証不要・X公式が提供する仕組みであり、規約上の自動投稿には該当しない(最後にタップして投稿するのは利用者自身)。利用者の「すぐコピーしてすぐ投稿」という要望に応えるための追加提案。
- 決定日: 2026-08-17
